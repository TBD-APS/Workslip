# Workslip demo on Azure Container Apps

This runbook owns the isolated public Workslip demo for WOR-392.

## Boundary

The demo is a disposable, synthetic-data environment. It must never share the production SQL database, storage account, application runtime identity or production application configuration.

Canonical Azure boundary:

- resource group: `rg-mrsoftware-demo`
- Container Apps environment: `cae-workslip-demo`
- Container App: `ca-workslip-demo`
- Azure SQL server: `db-mrsoftware-demo-server`
- Azure SQL database: `db-mrsoftware-demo`
- runtime identity: `id-workslip-demo`
- migration identity: `id-mrsoftware-demo-migration`
- deployment identity: `id-mrsoftware-demo-github`
- intended hostname: `demo.mrsoftware.dk`

The Container App contains two containers in one revision: an unprivileged nginx frontend on port 8080 and the Workslip API sidecar on port 5262. nginx proxies `/api/*` to the API over localhost, so the browser has one HTTPS origin and the API has no separate public ingress.

## Demo authentication

The API maps `POST /api/demo/token` only when both conditions are true:

1. `ASPNETCORE_ENVIRONMENT=Demo`
2. `DemoMode:Enabled=true`

The endpoint is absent in Development, Staging and Production even when the flag is set. It returns a normal Workslip JWT for the seeded demo administrator and is rate-limited per source IP.

The frontend exposes `Start demo` only when built with `VITE_DEMO_MODE=true`. Normal Microsoft/OTC login controls are hidden in this build. The normal product build remains unchanged.

Outbound invitation and OTC email is replaced with `DemoEmailService`, which deliberately does not send externally.

## Data and SQL access

The demo database uses the same reviewed, versioned migrations under `src/BE/infrastructure/database/migrations` and the same `run-database-migrations.ps1` migration history/checksum contract as the other Workslip environments.

SQL authority is split:

- `id-mrsoftware-demo-migration` is the Azure SQL Entra administrator and may run reviewed migrations.
- `id-workslip-demo` is the Container App runtime identity. The deployment grants it only `db_datareader` and `db_datawriter` inside `db-mrsoftware-demo`.
- the SQL bootstrap password exists only because Azure SQL server creation requires a bootstrap SQL administrator. It is stored only as the protected GitHub secret `DEMO_SQL_BOOTSTRAP_PASSWORD`; it is never passed to the Container App and is not used by normal migrations.

The API runtime connection string uses `Authentication=Active Directory Managed Identity` with the runtime identity client ID.

The seeded organization/jobs/users/customers are generated by the existing deterministic `DatabaseSeeder`. Demo startup explicitly invokes this seeder in the `Demo` environment. No production seed or export is used.

## GitHub environment

Create/protect a GitHub environment named `demo` before the first deployment. It needs:

- variable `AZURE_INFRA_CLIENT_ID`: the existing infrastructure bootstrap identity allowed to create the demo resource group and initial role assignments
- secret `AZURE_TENANT_ID`
- secret `AZURE_SUBSCRIPTION_ID`
- secret `DEMO_SQL_BOOTSTRAP_PASSWORD`: strong random value used only for the SQL server creation bootstrap

After the first foundation deployment, Bicep creates dedicated GitHub OIDC federations for `id-mrsoftware-demo-github` and `id-mrsoftware-demo-migration`. Normal image/app deployment and database migrations switch away from the broad infrastructure bootstrap identity to those dedicated identities.

## Deploy

After the change is merged to `main`:

1. Open GitHub Actions.
2. Select **Deploy Workslip Demo**.
3. Select `main`.
4. Leave **Recreate the isolated demo database** off for an ordinary release.
5. Run the workflow.

The workflow:

1. validates both demo Bicep templates;
2. reconciles the isolated foundation;
3. builds immutable frontend/API images in ACR tagged with the selected commit SHA;
4. applies reviewed migrations as the dedicated migration identity;
5. grants the runtime identity its contained database roles;
6. deploys the two-container Container App revision;
7. waits for `/login`;
8. obtains a demo token;
9. calls authenticated `/api/auth/me`;
10. prints the Azure demo URL and DNS handoff in the job summary.

No empty commit is required; this is a manual `workflow_dispatch` deployment handle.

## Reset

For a deterministic reset, run **Deploy Workslip Demo** with **Recreate the isolated demo database** enabled.

The destructive operation is hard-coded to all three of these values before it can execute:

- `rg-mrsoftware-demo`
- `db-mrsoftware-demo-server`
- `db-mrsoftware-demo`

The workflow deletes/recreates only that database, reapplies the reviewed migration set, recreates the runtime contained user and starts the new demo revision. The application then reseeds the canonical synthetic dataset. This code path cannot target production by input.

Existing orphaned demo blobs can be garbage-collected independently; they are not referenced after the database reset. Production storage is never addressed by this workflow.

## `demo.mrsoftware.dk` cutover

The first deployment exposes the Azure Container Apps FQDN in the Actions summary. Do not treat a CNAME alone as completed custom-domain setup: Container Apps must also own the hostname and certificate.

Cloudflare DNS should ultimately contain:

- CNAME `demo` -> the Container App FQDN emitted by the workflow
- the Container Apps domain-verification TXT record requested during hostname binding (normally an `asuid` record)

Then bind `demo.mrsoftware.dk` to `ca-workslip-demo` and provision/bind an Azure Container Apps managed certificate. Verify HTTPS at the custom hostname before changing the marketing CTA.

Cloudflare/DNS mutation is a separate live operation because DNS credentials are not stored in this repository.

## Rollback

Application rollback is an immutable-image redeploy of an earlier known-good commit SHA. Do not point the demo at production resources as a fallback.

Infrastructure rollback is either a forward Bicep correction or deletion of `rg-mrsoftware-demo`. Because the boundary contains only synthetic disposable data, no production restore procedure is coupled to demo recovery.

## Required verification

Before merge:

- backend build/tests including the demo environment guard;
- frontend typecheck/test/build;
- Bicep compilation for both demo templates;
- GitHub workflow syntax/policy checks.

After the first real deployment:

- frontend `/login` responds over HTTPS;
- `POST /api/demo/token` succeeds;
- authenticated `/api/auth/me` succeeds;
- normal production URLs do not expose `/api/demo/token`;
- one write flow is exercised in the demo;
- reset recreates the canonical demo dataset;
- `demo.mrsoftware.dk` is only advertised after custom-domain/certificate verification.
