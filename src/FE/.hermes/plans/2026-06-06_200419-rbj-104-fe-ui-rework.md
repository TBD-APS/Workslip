# RBJ-104 FE UI Rework Implementation Plan

> For Hermes: planning only. Do not implement until user explicitly approves. Do not commit or push. Prompt before creating/switching branch.

Goal: Improve the Workslip mobile job-flow UI so it is easier to scan, easier to tap, and visually calmer without changing core functionality or backend contracts.

Architecture: Treat RBJ-104 as a frontend-only visual/hierarchy pass centered on the job step UI, especially `Arbejdssedler` / timesheets. Keep current components and data flow. Prefer CSS and small markup/class changes over new abstractions.

## Product interpretation

This task is not “make it prettier”. It is “reduce mental work for the mobile user”.

The user should instantly know:
- Where am I in the flow?
- What is already saved?
- What can I edit right now?
- What is the primary next action?
- Are totals correct?

Non-goals:
- No backend changes.
- No API contract changes.
- No new design system package.
- No full rewrite of job flow.
- No hidden suppression of existing lint/React Doctor issues.
- No changing domain meaning unless wording is confirmed.

Open domain question:
- `sleptOnJob` is currently displayed as `Udlæg` in UI. Linear flags this as unclear. Before changing wording, confirm whether it means expense, overnight stay, allowance, or overnight expense. If user says it means overnight allowance, use `Overnattet` or `Overnatning / udlæg` consistently.

### Task 1: Set acceptance checklist before touching UI

Objective: Translate Linear’s broad UI notes into a tight checklist so the pass does not become endless taste-work.

Files:
- No source file changes unless documenting locally is requested.

Acceptance checklist:
1. Active step tab is visually obvious; inactive tabs are quieter.
2. Timesheet saved entries look like saved data, not forms.
3. Timesheet form looks editable and has consistent vertical spacing.
4. Only one strong primary action inside the form.
5. Labels are readable on dark background.
6. Touch targets are at least comfortable mobile size: buttons 44px-ish, icon buttons 40px-ish, inputs 44px-ish.
7. Summary totals are compact and fast to verify.
8. Border noise is reduced; background layering carries hierarchy.
9. `Udlæg`/`Overnattet` wording is consistent after domain confirmation.
10. Empty/loading/error states are clear and not spammy.

Verification:
- Manual visual review against each checklist item at mobile width and desktop width.

### Task 2: Improve top step tabs hierarchy

Objective: Make current step easy to spot without making all tabs compete visually.

Files:
- Modify: `src/features/jobs/components/steps/JobStepNavigation.tsx` only if extra ARIA/current metadata is needed.
- Modify: `src/App.css`, step indicator section around `.step-indicators`, `.step-dot`, `.step-dot.active`, `.step-dot.completed`.

Approach:
1. Keep current `JOB_STEPS` labels and icons.
2. Use inactive state as dark/subtle chip.
3. Use active state as the only bright selected chip.
4. Keep completed state useful but less loud than active state.
5. Add/verify `aria-current="step"` for active step if changing markup.
6. Ensure horizontal scroll remains comfortable on mobile.

Human impact:
- Low-to-medium severity UX issue. Users are not blocked, but they lose orientation and tap around more.

Verification:
- Open job detail at each step.
- Confirm only current step reads as selected.
- Confirm completed steps do not overpower active step.
- Confirm tabs remain horizontally scrollable on small mobile widths.

## Risks and tradeoffs

1. Dirty RBJ-55 branch risk:
   - Current branch/worktree is not clean. Biggest implementation risk is mixing unrelated UI work with RBJ-55.
   - Mitigation: do not start until branch strategy is approved.

2. Broad CSS selector risk:
   - `src/App.css` has many global selectors. Broad changes can unintentionally change other screens.
   - Mitigation: scope most changes to worksheet/job-step classes.

3. Wording risk:
   - `Udlæg` vs `Overnattet` has business meaning. Guessing can create real payroll/reporting mistakes.
   - Mitigation: ask once before changing label.

4. Visual-only task can sprawl:
   - Linear has 13 recommendation sections. Easy to keep tweaking forever.
   - Mitigation: implement high-priority items first, then stop after acceptance checklist is met.

5. Existing lint failures:
   - Lint already fails elsewhere.
   - Mitigation: record touched-file lint status separately; do not hide unrelated failures.
