# SDD Specification: RBJ-115 Passkey login

## 1. Goal
Invited users accept an invite by entering name/phone, then authenticating with Microsoft Entra/passkey, then receiving a normal internal Workslip JWT. Backend enrollment must revalidate invite state at callback time, create Entra + SQL user atomically enough to avoid orphaned Entra users when SQL persistence fails, mark invite consumed only after SQL success, and return the same `AuthTokenResponse` shape as existing login/invite flows.

## 2. Non-goals
- Do not rewrite existing email-code login.
- Do not change existing `/api/auth/verify-invite/{token}` response shape unless kept for backwards compatibility.
- Do not add AI/OCR scope. Selvfølgelig ikke.
- Do not touch unrelated jobs/audit/history features.
- Do not add new UI routes beyond the existing `/invite/:token` flow unless OAuth callback handling proves a dedicated callback route is required.

## 4. Architecture Decision
Backend: add `POST /api/auth/entra-enroll` and keep existing `/verify-invite/{token}` for compatibility. Enrollment accepts token/name/phone, requires a valid Entra bearer token, revalidates invite at execution time, starts an EF-backed transaction via an Application abstraction, creates/ensures Entra user, creates SQL user, marks invite consumed, commits, then returns `AuthUserInfo` mapped through existing `JwtHelper.GenerateToken` to `AuthTokenResponse`. If SQL/user/invite persistence fails after Entra creation, rollback transaction and call `DeleteUserAsync` to remove the Entra user.

Frontend: update `InviteAccept.tsx` into a two-phase flow. First collect/display persist name+phone+invite token in `sessionStorage`. Then start Microsoft OAuth authorization-code-with-PKCE flow using existing Azure/OAuth env vars. On return to `/invite`, exchange auth code for an Entra access token, call `/api/auth/entra-enroll` with explicit `Authorization: Bearer <entraAccessToken>`, store internal Workslip JWT, clean invite session keys and PKCE verifier, redirect to app/profile.

Reason: avoids sending PII in URL, preserves existing API shape, uses current combined auth scheme, and avoids Application depending directly on Infrastructure. The issue text says `oidc-react`; codebase says nope. Code wins. Fight me.

## 6. API Contract
### Request
`POST /api/auth/entra-enroll`
Headers:
```json
{ "Authorization": "Bearer <valid Entra access token>" }
```
Body:
```json
{
  "token": "invite-token-guid-without-dashes",
  "displayName": "Jane Jensen",
  "phone": "+45 12 34 56 78"
}
```
`phone` may be null/omitted/empty.

### Response
Same as existing auth responses:
```json
{
  "token": "<internal Workslip JWT>",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": {
    "userId": "guid",
    "organizationId": "guid",
    "email": "invitee@example.com",
    "displayName": "Jane Jensen",
    "role": "User"
  }
}
```

### Compatibility
- Preserve `/api/auth/verify-invite/{token}` response shape.
- Preserve `AuthTokenResponse` shape exactly.
- Preserve existing conflict codes: `invite_consumed`, `invite_expired`, `user_already_exists`.
- `POST /api/auth/invite/{token}/open` remains open/anonymous.

## 7. Data/Type Contract
- `EntraEnrollRequest.Token`: required non-empty string; maps to existing `InviteTokenRow.Token`.
- `DisplayName`: required non-empty after trim; max should respect `Users.DisplayName` max 200.
- `Phone`: optional; trim before save; max should respect `Users.Phone` max 80.
- `UserDataRow` remains unchanged.
- `InviteTokenRow` remains unchanged.
- Frontend sessionStorage keys must be namespaced, e.g. `workslip.inviteEnrollment` and `workslip.invitePkce`.
- Entra token must never be stored under `AUTH_TOKEN_KEY`; only final Workslip JWT goes there.

## 8. Behavior Rules
- Given invite token missing, when user opens `/invite/:token`, show invalid invite state.
- Given invite valid, when user enters name/phone and continues, save invite enrollment data to sessionStorage before redirecting to Microsoft.
- Given Microsoft returns with `code`, when sessionStorage invite data exists, exchange code for Entra access token, call `/api/auth/entra-enroll`, save internal JWT, cleanup temporary session keys.
- Given invite expired/consumed during Microsoft redirect, backend returns conflict code and frontend shows existing Danish message.
- Given SQL user creation or invite consumption fails after Entra user creation, backend rolls back SQL transaction and calls `DeleteUserAsync` for created Entra user.
- Given Entra user already exists because `CreateUserAsync` found existing one, cleanup delete must be careful: if service cannot distinguish created-vs-existing, spec requires either extend result with `Created` flag or avoid deleting pre-existing users. Better approach: extend `CreateEntraUserResult` with `bool Created` and only delete when `Created == true`.
- Given unknown Entra user hits `/api/auth/entra-enroll`, endpoint still may execute because it only needs valid Entra authentication and invite token; it must not require Workslip claims.
- Given old internal token is present in sessionStorage, enrollment call must explicitly override Authorization with Entra token.
